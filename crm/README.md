# Synapse CRM

Локальная CRM-часть проекта Synapse v1 prototype: FastAPI + PostgreSQL для учёта купленных/проданных игровых товаров, хранения рыночных объявлений, ценовых наблюдений, импорта от мониторинга и расчёта примерной экономики перепродажи.

CRM входит в монолитный проект `Monitor/Synapse`, поэтому обычно её не нужно запускать отдельно: используй общий скрипт из корня проекта.

## Быстрый запуск из корня

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start_all.ps1
```

Скрипт проверяет PostgreSQL, поднимает CRM на `127.0.0.1:8001` и запускает Telegram-панель управления мониторингом.

Страницы:

- `http://127.0.0.1:8001/bought` — купленные товары и остатки;
- `http://127.0.0.1:8001/sold` — проданные товары;
- `http://127.0.0.1:8001/stats` — статистика, графики, импортная аналитика;
- `http://127.0.0.1:8001/history` — история изменений и Bot API;
- `http://127.0.0.1:8001/market` — рыночные данные, сопоставления и очередь разбора.

## Данные и база

Основная база — PostgreSQL. Подключение задаётся в `.env` корня проекта:

```text
DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/crm_inventory
```

SQLite в v1 остаётся только как старый/тестовый формат и не должен быть основной базой рабочего монолита.

В репозиторий не кладём реальные базы, дампы, `.env`, логи и полную историю объявлений. Для демонстрации формата есть только маленькие обезличенные примеры в `examples/`.

## Bot API

Мониторинг сайта вторичного рынка отправляет найденные объявления в CRM:

```text
POST http://127.0.0.1:8001/api/market/imports/avito
```

Проверка состояния импортов:

```text
GET http://127.0.0.1:8001/api/market/imports/avito/summary
```

Оценка одного объявления:

```text
POST http://127.0.0.1:8001/api/market/evaluate-avito-listing
```

Если в `.env` задан `MARKET_IMPORT_TOKEN`, к запросам нужен заголовок:

```text
Authorization: Bearer <MARKET_IMPORT_TOKEN>
```

В локальном прототипе токен можно не задавать, если CRM и бот работают на одном ПК.

## Что делает CRM

- хранит личные покупки и продажи отдельно от внешней аналитики;
- принимает объявления от мониторинга и дедуплицирует их по внешнему ID/URL/fingerprint;
- сохраняет raw payload объявления для аудита;
- хранит ценовые наблюдения и использует их для примерных рыночных цен;
- ведёт каталог, алиасы и очередь ручного разбора неоднозначных товаров;
- оценивает объявление только по уверенно распознанным товарам;
- не должна считать профит по generic-only строкам вроде “игры”, “диски”, “PS4/PS5” без конкретного названия.

## Режимы мониторинга

Telegram-панель умеет запускать поиск:

- с анализом — LLM извлекает товары, CRM считает оценку/профит, в Telegram приходит отдельное сообщение анализа;
- без анализа — объявления сохраняются и приходят в Telegram, но LLM и платная оценка пропускаются.

Это нужно, чтобы можно было быстро мониторить выдачу без расхода баланса на модель.

## Внутренняя структура

- `app/main.py` — FastAPI-приложение и маршруты;
- `app/models.py` — SQLAlchemy-модели;
- `app/inventory.py` — покупки, товары, продажи, экспорт;
- `app/market.py` — импорт/дедупликация рыночных данных;
- `app/avito_evaluator.py` — оценка объявления, price matching, anti-false-match правила;
- `templates/` — Jinja2-страницы CRM;
- `static/` — liquid-glass стили, JS и логотип;
- `tests/` — регрессионные тесты CRM.

## Проверки без запуска сервера

```powershell
python -m py_compile crm\app\main.py crm\app\avito_evaluator.py
python -m pytest -q crm\tests
```

Эти команды не поднимают CRM-сервер и подходят для быстрой проверки перед коммитом.
